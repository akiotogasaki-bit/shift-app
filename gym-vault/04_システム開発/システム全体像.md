# システム全体像

## 構成（お江戸弁当と同構成を踏襲）

```
  ［会員］                          ［妻（トレーナー）］        ［社長］
     │ LINE                              │ ブラウザ                │ ブラウザ
     ▼                                   ▼                         ▼
  reserve.html  mypage.html         trainer.html             admin.html
  （LIFF・予約）（残回数・記録）   （当日の予約・記録入力）  （会員・請求・KPI）
     │              │                    │                         │
     └──────────────┴────────────────────┴─────────────────────────┘
                                 │  fetch (JSON)
                                 ▼
                   Google Apps Script  （doGet / doPost）
                                 │
                                 ▼
                   Google スプレッドシート（＝DB）
                     会員 / プラン / 契約 / 月次残高 /
                     枠マスタ / 休業日 / 予約 /
                     セッション記録 / 請求 / 操作ログ
                                 │
                                 ▼
                   LINE Messaging API（予約確認・前日リマインド）
```

配信は **GitHub Pages**（HTMLを置くだけ）。決済は **Stripe**（未決・未決#8）。

## この構成を選ぶ理由

| 理由 | 内容 |
|---|---|
| 社長がすでに運用できる | お江戸弁当で実運用中。学習コストゼロ、トラブル対応の勘が効く |
| 月額コストがほぼゼロ | GAS・スプレッドシート・GitHub Pagesはすべて無料枠。予約SaaSは月5,000〜20,000円かかる |
| **妻がDBを直接見られる** | スプレッドシートなので、システムが詰まっても妻が手で直せる。開業初期はこれが最大の価値 |
| LINEと直結 | 会員の生活動線に予約とリマインドを乗せられる。アプリのインストールが不要 |
| ビルド不要 | 1画面1HTML。修正してpushすれば即反映 |

## この構成の限界（先に把握しておく）

| 限界 | いつ問題になるか | その時の対応 |
|---|---|---|
| GASの実行時間・同時実行の制約 | 会員数が数百名規模になったら | 会員27名が天井の事業なので、**当面問題にならない** |
| スプレッドシートの同時書き込み | 妻と会員が同時に同じ行を書く時 | LockServiceで予約確定処理を直列化する（必須） |
| 二重予約 | 同じ枠に2名が同時申込 | 予約確定は必ずサーバ側（GAS）で枠の空きを再確認してから書く |
| 認証の弱さ | 会員情報が推測で見られるリスク | LIFFのIDトークン検証を必須にする。URLに会員IDを直書きしない |

## 作る順番（これを守る）

```
Phase 1（開業3か月前）  予約が取れる最小構成
  ├ 枠マスタ・休業日の登録（妻がスプレッドシートで直接）
  ├ reserve.html     会員が空き枠を見て予約・キャンセル
  ├ trainer.html     妻が当日の予約を見る
  └ LINE 予約確認通知

Phase 2（開業1か月前）  会員とサブスクの管理
  ├ 会員登録・プラン紐付け
  ├ 月次残高（付与・消化・繰越）
  ├ mypage.html      残回数・予約履歴
  └ admin.html       会員一覧・状態変更

Phase 3（開業後1〜2か月）  記録と請求
  ├ セッション記録（体重・体脂肪・種目）
  ├ 体組成の推移グラフ（mypage.html）← 継続率に直結
  ├ 請求の月次締め
  └ 稼働率・チャーンのダッシュボード

Phase 4（必要になったら）
  ├ Stripe 自動課金連携
  ├ 前日リマインド自動送信
  └ 体験申込フォーム → 入会導線
```

### 作らないもの（意図的に）

- 独自のネイティブアプリ（LINEで足りる）
- トレーナー複数名のシフト管理（妻1人のうちは不要。2室目を出す時に作る）
- オンラインでの初回カード登録フロー（Phase 4まで手動で十分）
- 会員同士のSNS機能・ランキング（完全個室の価値観と合わない）

> **原則：紙とLINEで回らない業務は、アプリにしても回らない。** Phase 1より前に、妻が紙で1週間分の予約を回せるか確かめる。
